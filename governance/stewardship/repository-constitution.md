# Repository Constitution

## The Restoration Community Repository as Institutional Memory

This repository is the canonical home of the Restoration Community's institutional memory.

It is not merely a place to store code.

It is a permanent record of how the Restoration Community was built, governed, and stewarded over time.

---

# Purpose

This repository exists to:

* **Preserve** the foundational documents that define the Restoration Community
* **Trace** how every significant decision was made and why
* **Guide** future stewards, contributors, and maintainers
* **Protect** the integrity of the mission as the community grows
* **Honor** the stewardship work of every person who has contributed

---

# Governance Hierarchy

The repository reflects this authority hierarchy:

```
Scripture
    ↓
Four-Book Foundation
    ↓
Constitutional Preamble
    ↓
Repository Constitution
    ↓
Restoration Community Engineering Charter
    ↓
Engineering Constitution
    ↓
Product Requirements Baseline
    ↓
Technical Architecture
    ↓
Operational Constitution
    ↓
Implementation
    ↓
Tests
```

Every document's authority derives from its position in this hierarchy.

Documents higher in the hierarchy take precedence over documents lower in the hierarchy.

---

# Canonical Home Principle

Every document has one authoritative location within this repository.

Information appears once.

Other documents reference it.

No duplication.

This principle prevents contradictions and makes the repository easier to maintain.

---

# Commit Discipline

Every commit should tell the story of the project.

Commits should:

* Be focused (one coherent change per commit)
* Be meaningful (commit message explains why, not just what)
* Be traceable (future stewards can understand the decision)
* Be atomic (the repository is always in a valid state after each commit)

The commit history becomes a chronicle of stewardship.

---

# Document Authority & Status

Every document in governance/ includes metadata:

* **title** — the document's name
* **status** — Approved, Draft, or Archived
* **version** — using semantic versioning
* **owner** — the steward role responsible for the document
* **last-reviewed** — when it was last reviewed and approved

This metadata ensures clarity about which documents are binding and which are evolving.

---

# Review Before Migration

Before any document is committed to the repository:

* It must be reviewed for alignment with the Four-Book Foundation
* It must be checked for consistency with documents higher in the hierarchy
* It must be approved by the appropriate Governance Stewards
* It must have clear metadata and proper Markdown formatting

The repository should only contain documents that have been carefully stewarded.

---

# Future Amendments

When governance documents are amended:

* Changes should be committed separately (not batched)
* The commit message should explain why the change was necessary
* Version numbers should increment to reflect the change
* The last-reviewed date should be updated
* Previous versions may be archived rather than deleted

This preserves the history of how the document evolved.

---

# Stewardship Over Time

This repository is a multi-generational project.

Future stewards may:

* Inherit this repository
* Contribute to it
* Improve it
* Extend it

The discipline we establish now will shape how well they can steward it later.

Every commit, every document, and every design decision should reflect faithful stewardship.

---
